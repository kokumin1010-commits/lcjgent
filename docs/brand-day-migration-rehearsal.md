# KGDAY → LCJ 原生迁移预演记录

## 清单与隐私控制

KGDAY 源数据通过沙箱外部脚本导出到 `/home/ubuntu/kgday_migration/kgday-manifest.json`，权限为 `0600`。清单不进入 Git，不作为构建产物，也不会在 LCJ 页面中显示个人资料或密码哈希。现有 bcrypt 哈希原样迁移，因此创作者不需要重设密码。

真实 LCJ Zod 与权限端点对完整清单执行了哈希和引用预检。结果为 `valid=true`，缺失截图URL、无效账号引用和无效商品引用均为0。42张对象存储原图均已从短时签名地址读取并重新计算 SHA-256；清单哈希保存在本地摘要中，不在文档回显任何对象地址或个人资料。

## 隔离数据库预演

本地建立独立 MariaDB `lcj_brandday_test`，应用 `0139_brand_day_native.sql` 后确认8张 `brand_day_*` 表全部创建。集成测试使用一套隔离记录和模拟对象存储执行以下流程：管理员预检、图片SHA-256核对、活动/报名/账号/成绩/商品/审计事务导入、来源ID映射、目标计数核对、同一 `migrationKey` 第二次执行幂等返回，以及测试数据清理。

首次预演发现 ISO 8601 字符串不能直接写入 MySQL/MariaDB `timestamp`。迁移端点已统一在写入前转换为 JavaScript `Date`，重跑后全部通过。完整 LCJ 构建同时保持 `DATABASE_URL` 未设置，确认不会再误连 KGDAY 数据库。

## 生产执行门槛

生产导入必须在 LCJ schema 发布完成后，由已登录管理员从「ブランドデー一覧」选择最新迁移清单。页面先显示六类计数并验证全部引用，再允许执行。执行时42张原图会下载、复核SHA-256并写入 LCJ R2；数据库事务完成后按来源ID统计26/26/42/81/164和42张原图。任何数量或哈希不一致都会将迁移批次标记为失败，且不得切换主数据源。

## 生产执行结果

PR #27 合并后，`lcjmall.com` 已部署「ブランドデー一覧」及全部公开/创作者路由。初次生产检查发现 Railway 未运行仓库迁移脚本，公开 API 返回 `brand_day_events` 缺表500；随后增加了监听前的 CREATE-only 幂等建表守卫。该守卫在空白 MariaDB 创建并验证8张 `brand_day_*` 表，重复执行不产生变化，且明确拒绝 DROP、ALTER、INSERT、UPDATE 等非建表语句。生产重新部署后 API 由缺表500变为正常的活动未导入404，证明 schema 已就绪。

全量迁移通过短时单用途令牌执行。服务端先验证清单规范哈希与全部引用，再逐张下载42张原图并复核 SHA-256，写入 LCJ 对象存储后在事务中导入26报名、26账号、42成绩、81商品和164审计。目标计数与源计数六项完全一致，eventId 为1，迁移批次状态为 completed。排行榜源目标匿名汇总也完全一致：销售榜4行、配信榜4行、KG GMV 35,201、有效配信2,684分钟。

迁移成功后立即移除短时生产端点及部署代码中的令牌哈希，并验证该路径不再由服务器处理；本地0600清单、请求、响应、明文令牌、临时浏览器诊断脚本和3个隔离测试数据库均已删除。LCJ 公开活动、报名、创作者登录、排行榜和管理页面路由继续返回 HTTP 200。

独立 KGDAY 站随后通过 Manus 检查点 `03900dc2` 切换为只读回退：所有页面显示 LCJ 迁移提示并链接到对应原生页面；报名、创作者上传和管理员写入由服务端统一拒绝。生产状态为 `migrated-read-only`，历史销售榜与配信榜继续各返回4行。正式报名与上传探测均返回 `FORBIDDEN`，证明 LCJ 已成为唯一可写主数据源且不会继续双写。
