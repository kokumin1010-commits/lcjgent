# 收据审核规则 V2 实现规范

## 目标与边界

本次只改变新提交及后续审核流程，不批量修改现有 `on_hold`、`pending`、`approved` 或 `rejected` 记录，不创建测试收据，不在生产环境发放测试积分。生产数据库继续仅使用 Railway MySQL，禁止连接旧 TiDB。

规则必须由服务端统一执行，网页上传、LINE 上传、后台重识别、AI 自动审核和管理员通过不得各自维护不同的重复判断。

## 必要证据

一张可通过的收据必须同时具备：TikTok Shop 订单详情证据、已配达或等价完成状态、规范化订单号、正数合计金额、至少一张可读取图片，并且不存在阻断性订单号冲突或硬风险。

多张图片视为一个证据组，必须整体识别。任何单张图片缺字段，只要其他同组图片补齐，不应拒绝。

## 订单号规范化

订单号先去除空格、横线和非数字字符。有效订单号为 16–19 位数字；首位 5 或 6 为强特征，但不作为唯一拒绝条件，以兼容已存在的有效订单格式。规范化后的值用于全部查询和比较。

## 同一订单号状态矩阵

| 已存在记录 | 同账户新提交 | 其他账户新提交 |
|---|---|---|
| `approved` | 阻止 | 阻止 |
| `pending` | 阻止 | 阻止 |
| `on_hold` | 阻止并继续处理原记录 | 阻止并标记跨账户冲突 |
| `rejected` | 允许修正后重新提交 | 阻止 |

同账户例外只在既有同订单号记录全部为 `rejected` 时成立。如果同账户同时存在任何 `approved`、`pending` 或 `on_hold`，不得创建新的有效申报。

跨系统旧 `point_requests` 继续参与防重复。能够可靠映射为同一会员且旧申请为 `rejected` 时允许重传；身份无法可靠映射时采用安全侧规则，不自动放行。

## 并发安全

订单号判断与当前收据保存必须按规范化订单号串行化，防止两个不同账户同时完成识别后均通过查询。实现应使用 Railway MySQL 同一连接上的命名锁或等价事务锁，在锁内重新查询现有记录、作出判定并保存当前订单号，最后释放锁。锁获取失败或重复查询失败时不得自动通过或发积分，应进入技术重试并最终拒绝重传。

## 技术重试

AI 调用、响应解析或图片读取失败时自动重试一次。两次尝试必须使用全部图片和严格 JSON Schema。第二次仍失败则：若原图可访问但必要字段无法识别，状态改为 `rejected`，原因是技术识别失败并要求重传；若原图损坏或不可访问，状态改为 `rejected`，原因是原图损坏并要求重传。

数据库查询、重复检查、状态写入或积分写入失败属于基础设施错误，绝不能绕过检查自动批准。失败时保持未发积分，并记录可重试错误；不得采用“重复检查失败也继续批准”的旧行为。

## 强制申诉

强制申诉不得因为用户点击申诉就直接进入永久暂挂。系统必须读取原拒绝原因和当前证据。只有当新证据或重新识别结果解决原拒绝原因，并满足全部必要证据时才可通过；原问题未修正或仍缺必要信息时拒绝并明确要求重传。

若当前强制申诉接口没有新增图片或证据，则不能声称用户已修正；应拒绝并引导通过正常上传入口提交修正后的图片。同一账户旧记录为 `rejected` 时，正常重传应允许。

## 风险分层

硬风险仅包括确定重复订单号、确定同图复用、明确跨账户冒用、图片明显篡改或会员积分限制。硬风险不得自动通过。

高金额、订单超过 30 天、短时间多次提交、相似订单号、店铺名称缺失属于软风险，只触发日志或人工抽样，不得单独造成长期 `on_hold`。证据齐全、无阻断性重复且无硬风险时，应按正常审核结果出队。

## 最终状态

| 情况 | 结果 |
|---|---|
| 必要证据齐全、无冲突、无硬风险 | `approved`，按既有幂等流程发放 1% 积分 |
| 非 TikTok Shop、未配达、缺订单号、缺金额、图片不可读或技术重试仍失败 | `rejected`，提供明确重传原因 |
| 跨账户冲突、强制申诉且存在新证据、硬风险需管理员判断 | `on_hold`，必须记录具体原因、下一步、负责人和截止时间 |

新流程不得仅因为置信度处于中间区间而无期限暂挂。置信度只作为是否需要第二次识别或人工抽样的依据，不能替代业务证据判断。

## 只读预演

任何对历史暂挂队列的批量处理必须先提供只读预演，至少返回候选数量、预计通过数、预计拒绝数、仍需人工数、预计积分总额、LINE 通知数和原因分布。预演不得写状态、OCR、积分、审核日志或通知。执行历史队列必须另行得到用户明确授权，本次部署不自动执行。
