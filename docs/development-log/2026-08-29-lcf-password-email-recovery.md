# LCF パスワード・メール復旧システム改善記録

## 概要

2026年8月29日、複数のLCF利用者から「パスワード再設定メールが届かずログインできない」「マイページでパスワードを変更したが確認メールが届かない」との報告があった。個別アカウントだけを手動変更するのではなく、企業・ライバー・一般・管理者の全アカウントに共通する認証・メール復旧経路を調査し、恒久対策を実装した。

## 根本原因

| 項目 | 調査結果 |
|---|---|
| マイページのパスワード変更 | パスワード自体は変更されるが、確認通知メールは実装されていなかった。 |
| 忘れたパスワード | 一次修正で安全なワンタイムリンク方式になったが、SMTPが受け付けたか、失敗したかを管理者が確認できなかった。 |
| SMTP選択 | Gmail設定が存在すると企業メール設定を使わず、最初の設定が壊れている場合に別経路へ切り替える仕組みがなかった。 |
| 管理者の旧PWリセット | 明文の一時パスワードを生成・表示し、本人が受け取る前に既存パスワードを無効化する危険な方式だった。 |
| 受信ドメイン認証 | `livecommercejapan.jp` のMXとSPFは阿里企業メールに一致する一方、公開DMARCレコードは確認できなかった。DKIMは既知の一般的なセレクターでは確認できず、メール管理画面側での確認が必要。 |

## 実装内容

メールサービスは阿里企業メールを優先し、認証・接続・DNS・タイムアウトなどの配送経路障害に限りGmail予備経路へ切り替える。宛先拒否などメッセージ固有の失敗では二重送信を避けるため切り替えない。結果として、提供者、SMTPメッセージID、安全化したエラーコードを返す。

LCF専用の `festival_email_delivery_logs` を追加した。完全な宛先メールアドレスは保存せず、アカウントID、宛先SHA-256、ドメイン、用途、起点、SMTP受付または失敗、提供者、メッセージID、エラーコードを記録する。

公開の忘れたパスワード機能は、1時間有効・1回のみ使用できるワンタイムリンクを使用し続ける。メール失敗時は令牌を直ちに無効化し、既存パスワードを変更しない。公開応答はアカウント列挙を防ぐため存在・不存在・配送失敗で統一する。

マイページのパスワード変更と、ワンタイムリンクからの再設定完了後には確認通知を送る。通知が失敗しても、既に完了したパスワード変更を失敗扱いにせず、新しいパスワードと必要なセッション状態を維持し、画面に正確な結果を表示する。

管理者の旧「PWリセット」は廃止し、本人宛てにワンタイム再設定リンクを送る方式へ変更した。リンク送信前に確認ダイアログを表示し、本人がリンクを使い終えるまで現在のパスワードを変更しない。

管理画面のアカウントタブに、阿里企業メールとGmail予備経路の設定状態、直近のSMTP受付・失敗数、アカウントごとの最新メール状態、詳細なパスワード関連メール配信ログを追加した。操作履歴にも再設定リンク送信、再設定完了、パスワード変更、変更通知失敗を表示する。

## データベース変更

`drizzle/0127_lcf_email_delivery_audit.sql` を追加し、Drizzle journalへ順序登録した。実行時の幂等Schema確認にも同一テーブル定義を追加した。既存のLCFアカウント、申込、予約、GMV、Ticketのデータは変更しない。

## 検証

ローカルの純粋テストでは実メールを送らず、阿里優先、認証失敗時のGmail切替、宛先拒否時の二重送信防止、SMTP未設定時の安全な失敗を検証した。LCFセキュリティ、予約、一般申込を含む32項目の回帰テストが合格し、認証ルーター、メールサービス、管理画面、マイページ、重置页面の分割ビルドも成功した。

## 運用とロールバック

本番ではGitHub mainからRailwayへ自動デプロイする。デプロイ後は、無実在の予約済みドメインアドレスでアカウント列挙防止を検証し、管理画面でSMTP設定状態と配信ログを確認する。実在ユーザーへの送信は管理者の確認後に個別実施し、一括PW変更や一括メール送信は行わない。

重大な回帰があれば本変更コミットをrevertする。0127テーブルは既存機能から独立しているため、コードをrevertしても既存認証データに影響しない。テーブル削除は監査データを失うため、自動ロールバックでは実行しない。
