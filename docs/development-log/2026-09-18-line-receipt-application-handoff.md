# LINEレシート申請導線・受付追跡の修正

## 概要

2026年9月18日、LINEユーザーから「9月6日と13日にポイント申請したが、承認通知もポイント加算もない」と問い合わせがあったため、LINEメッセージ、レシート申請、旧ポイント申請、会員ポイント履歴を本番でread-only照合した。

## 調査結果

対象会員はLINE確認済みの単一会員として存在し、現在ポイントは4,188pt、ポイント履歴は2件だった。レシート履歴は392件あるが、最新の実レコードは2026年8月22日であり、2026年9月6日・13日のLINEレシート、Webレシート、旧ポイント申請レコードはいずれも存在しなかった。したがって、注文番号・購入金額・原画像などの根拠がない状態でポイントを補填すると二重付与の可能性があるため、本番ポイント書込みは行っていない。

直接原因は、8月31日以降のLINE画像受信フローが画像を申請レコードへ変換せずWebフォームへ案内する設計である一方、返信冒頭が「レシート画像を受け取りました」と受理済みに見える表現だったこと、さらに案内URLが旧Base64形式の無署名tokenを生成していたことにある。サーバー側は同時点で無署名bearer tokenを意図的に拒否していたため、LINE内ブラウザからWebフォームへ遷移しても認証できず、申請レコードが作成されない状態になり得た。

## 修正

LINE画像受信時は、サーバー検証可能な署名済み会員tokenを発行し、同一LINE会員のWeb申請フォームへ引き継ぐ。返信文は「LINEへの画像送信だけでは申請未完了」と明示し、Webフォームで「申請を受け付けました」と受付番号が表示されるまでレコードが作成されないことを説明する。画像受信イベント自体は、スタッフが後日確認できるよう「LINE送信のみでは申請未完了・Webフォーム案内済み」としてメッセージ履歴に監査保存する。

Webフォームが申請レコード作成に成功した場合は、永続化済み`receiptId`を「受付番号 #...」として画面とtoastに表示する。問い合わせ時にこの番号を使って申請を一意に照合できる。管理画面のレシート検索は、直接LINE identityだけでなく`email_<memberId>`別名で保存されたレコードも会員表示名・identity keyで検索できるようにした。
