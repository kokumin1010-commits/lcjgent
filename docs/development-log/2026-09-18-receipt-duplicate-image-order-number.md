# レシート重複画像・注文番号認識の修正

## 概要

2026年9月18日、同一アカウントから同じ注文画像が二度申請されているにもかかわらず、AI OCRが注文番号を一桁違いで読み取り、後発申請が即時却下されず保留になる事象を修正した。

根本原因は、既存処理が画像バイト列のSHA256完全一致を検出済みでも、それを補助フラグとして扱い、後続のAI OCRと注文番号判定を優先していたことにある。同一画像に対する二回のOCR結果が一致しない場合、画像証拠より不安定なOCR候補が優先され、後発申請が「類似注文番号」として保留される余地があった。

## 実装

完全一致画像は、レシート行を作成した直後かつAI OCR開始前に検索する。現在の受付番号より小さい、却下されていない最古の申請を正本とし、後発申請を自動却下する。同時刻に二件送信された場合も、受付番号の小さい一件だけを正本として残すため、相互却下は発生しない。過去の却下済み申請は比較対象外であり、画像を修正した再申請を妨げない。

画像が再圧縮・リサイズされSHA256が変わった場合には、OCR前に知覚ハッシュを比較する。誤検知を避けるため、既存の一般判定閾値より厳しいハミング距離0〜1だけを「同一視覚証拠」として後発申請の自動却下に使用する。

自動却下時には、後発申請で再度OCRした番号を正本として採用しない。先行する有効申請のDB標準注文番号、金額、店舗を継承し、重複元受付番号、判定方式、OCR候補番号を監査用JSONと不正検知ログへ保存する。ポイント計算は0、状態は`rejected`、不正スコアは100とする。

注文番号占有ロックは、注文番号だけでなく金額と店舗も同一トランザクション内で保存するようにした。これにより、ほぼ同時に同一注文を送信し、OCR結果が一桁だけ異なった場合も、同一金額を根拠として二件目を`same_account_similar_order_number`または`cross_account_similar_order_number`で阻止できる。阻止された行には先行申請の標準注文番号を保存し、誤読した値は`ocrOrderNumberCandidate`として分離する。

ユーザー画面は、SHA256完全一致を同期検出した場合に緑色の「受付完了」を表示せず、赤色の「重複申請のため自動却下しました」を表示する。却下申請は確変・抽選へ進めない。管理画面は`line_receipts.orderNumber`を常に標準値として優先し、異なる旧OCR値が残る場合のみ「OCR候选号」と明示する。
