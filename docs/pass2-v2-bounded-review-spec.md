# 历史暂挂 AI 再审查 V2：安全分批与确认契约

## 目标与边界

本次将历史 `on_hold` 收据的真实再审查完全接入新收据审核 V2。点击入口首先只生成只读预演；只有管理员检查固定候选样本、勾选确认并提交有效批次令牌后，才能改变状态、发放积分或发送通知。系统不得一次处理全部 14,614 条，本次不自动执行任何生产批次。

生产数据库继续仅使用 Railway MySQL，禁止连接旧 TiDB。实现不新增表、不修改既有流水，不创建测试收据或测试积分。

## 固定批次契约

| 项目 | 规则 |
|---|---|
| 单批数量 | 管理员选择 10、25、50 或 100 条；后端强制 `1..100`，默认 25 |
| 候选顺序 | 只选择当前最早提交的 `on_hold` 记录，按 `submittedAt ASC, id ASC` |
| 预演 | 返回全队列总量、本批候选、类别、脱敏订单号尾号、金额、预计积分和样本图片数量；不写任何数据 |
| 确认令牌 | 服务器用 HMAC 签名候选 ID、状态指纹、数量和十分钟有效期；令牌不能伪造或更换候选 |
| 执行校验 | 开始前重新读取固定候选。任何记录不再为 `on_hold` 或关键状态已改变时，该记录跳过，不处理新补入记录 |
| 并发 | 同一实例只允许一个 Pass 2 批次；订单号仍使用 Railway MySQL 命名锁跨实例串行检查 |
| 停止 | 管理员停止后，当前单条完成即中止后续记录，不再仅改变前端标志 |

## V2 决策规则

每条候选最多使用两次严格结构化多图识别。全部图片作为同一证据组，第二次只补全第一次缺失字段。

| 条件 | 结果 |
|---|---|
| 无图片、图片损坏或两次技术重试仍无法取得主要信息 | `rejected`，明确要求重新上传 |
| 明确不是 TikTok Shop 订单详情 | `rejected` |
| 明确未配达 | `rejected` |
| 两次识别后缺16–19位订单号 | `rejected`，要求重传订单号清晰页面 |
| 两次识别后缺合计金额 | `rejected`，要求重传合计金额页面 |
| 多图合并后四项证据齐全 | 进入订单号并发检查 |
| 订单号属于其他账户，任何历史状态 | `on_hold`，标记跨账户冲突、阻断记录和72小时人工复核路径 |
| 同账户存在待审、暂挂或已通过记录 | `on_hold`，标记同账户有效冲突，人工选择保留哪条；不得重复发分 |
| 同账户仅有已拒绝历史或无历史冲突 | 使用统一 V2 批准服务通过 |
| 精确图片复用或其他硬风险成立 | `on_hold`，写明硬风险、证据、负责人待定和72小时期限 |
| 强制申诉 | 不自动永久保留；重新识别后证据齐全则进入正常订单号检查，仍缺必要信息则拒绝重传；硬风险才暂挂 |

通过必须复用 `approveReceiptFromEvidence`：最终订单号检查、1%积分幂等守卫、批准状态、审核日志、推荐确认、商品提取、自动评价和可选通知保持一致。拒绝必须写明确类别和重传理由，并按批次配置发送通知。

## 预演与真实执行的区别

预演只依据数据库已有字段进行初步分类，并明确标为预计结果；真正执行会重新读取全部图片并最多调用两次AI，因此最终类别可能变化。预演令牌只固定候选集合与状态，不承诺AI判断结果。

真实执行按钮必须同时满足：预演成功、令牌未过期、候选未改变、管理员输入固定确认短语、勾选理解“会修改状态、发放积分、发送通知”，并且批次数量不超过100。

## 验收

测试必须覆盖跨账户任意状态冲突、同账户有效冲突、同账户已拒绝可重审、强制申诉证据齐全/不全、技术重试、无图、非TikTok、未配达、缺订单号、缺金额、多图合并、批准积分幂等、拒绝通知、100条上限、令牌篡改/过期/状态变化、真正停止和只读预演零写入。生产验收只使用GET或未认证权限探测，不执行真实Pass 2。
