# LCF 跨届个人档案与 Guidance 架构

## 目标

LCF 官网以品牌为长期主体，每一届活动拥有独立、永久的活动主页、開催レポート与 Guidance。登录用户的マイページ不再只呈现“当前一届”，而是以届次显示本人真实参加记录，并在下一届开放报名后自动增加新记录。

## 永久 URL 体系

| 用途 | URL | 规则 |
|---|---|---|
| LCF 品牌总入口 | `/`、`/livecommercefestival` | 展示最新消息、历届档案和下一届咨询入口 |
| 第1回原活动主页 | `/livecommercefestival/2026` | 永久保留，不被后续届次覆盖 |
| 第1回短链接 | `/2026` | 打开与原活动主页相同的页面，便于分享 |
| 第1回開催レポート | `/livecommercefestival/2026/report` | 真实成果、精选照片、媒体报道和官方照片下载 |
| Guidance 总入口 | `/lcf/guidance` | 展示最新可用 Guidance 与历届 Guidance 档案 |
| 第1回 Guidance | `/lcf/guidance/2026` | 永久保留当前完整指南，不被第2回覆盖 |
| マイページ | `/lcf/mypage` | 登录后按届次显示本人申请、票券、受付和预约历史 |

未来届次确认年份后，按同一规则增加`/{year}`、`/livecommercefestival/{year}`、`/livecommercefestival/{year}/report`和`/lcf/guidance/{year}`。在日期、场地和报名范围未正式确定前，不创建虚假的第2回活动记录。

## マイページ数据契约

`festival.getMyEditionHistory`按当前登录邮箱读取三类申请表中的全部`eventYear`记录，并按届次返回共同字段：申请类型、申请状态、申请日期、票券数量、累计受付人数、初次／最后受付时间。直播ブース预约继续使用既有`boothReservation.getMyReservations`，由活动日期映射到对应届次，在客户端汇总预约数、已签到数与取消数。

第1回现有编辑功能、QR、累计受付、预约创建与取消仍使用原API；新的历史API只读，不改变任何申请、票券、预约或签到记录。`lcf_tickets`当前未保存`eventYear`，因此历史查询通过`applicationId + applicantType`回连对应申请表取得届次，避免为第一届档案新增高风险迁移。未来建票时继续保持申请与票券关联即可自动归档。

## Guidance 版本策略

现有`LcfGuidance`作为2026内容组件，由`/lcf/guidance/2026`直接渲染。新的`/lcf/guidance`为档案入口：第一届卡片显示開催終了与永久查看按钮；下一届 Guidance 发布后增加新卡片并将其标记为最新，而不是修改2026内容。

マイページ每届卡片提供该届活动主页、開催レポート和Guidance入口。未发布的资源不显示可点击按钮，只显示“公開準備中”，避免死链接。

## 官方照片下载

第1回档案保存798张公开高清原图，共9个ZIP分卷、4.19 GiB。每个分卷包含照片、`manifest.json`、`manifest.csv`与日文说明；官网同时提供总清单、`SHA256SUMS.txt`和第三方完整相册浏览入口。官网精选画廊继续使用48张优化图片，避免首页和报告页一次加载4.19 GiB原图。

人物照片的公开下载页必须明确：可用于活动回顾、关系者共享与LCF介绍；再次公开时需尊重肖像权与隐私，不得用于诽谤、虚假表示或素材转售。

## 保护边界

报名、登录、密码重置、管理员后台、入场受付、累计人数、旧二维码、VIP、アフターパーティー、ブース预约与签到路径保持不变。跨届档案新增功能均为只读展示；任何未来届次的正式报名、票券发行或生产写入必须在对应届次确认后另行实施和验证。
