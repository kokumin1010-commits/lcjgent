# 暂挂订单人工学习审核规范

## 目标

`/master/receipts` 的“学习审核”只处理 **AI无法独立判断且仍处于 `on_hold` 的订单**。AI已经自动通过、自动拒绝或能够依据现行规则得出结论的订单，绝不进入学习队列，也不写入人工学习案例。

## 学习队列准入

一条记录必须同时满足以下条件才可显示：

| 条件 | 必须值 |
|---|---|
| AI批次 | `aiPass = 2` |
| 执行模式 | `isDryRun = false` |
| 原状态 | `beforeStatus = on_hold` |
| AI处理后状态 | `afterStatus = on_hold` |
| AI决定 | `keep_manual` 或兼容旧值 `held` |
| 人工处理 | `humanOverride IS NULL` |
| 当前收据状态 | `line_receipts.status = on_hold` |

`auto_approved`、`auto_rejected`、`approved`、`rejected_*`、`skipped`、`STOP_REQUESTED`、`STATE_CHANGED` 与普通AI自动审核日志全部排除。

## AI问题点

学习审核卡片必须显示AI已知信息和无法判断的问题。问题点由服务器根据 `reasonCode`、AI理由和当前证据生成，前端不得自行猜测。

| 原因码 | 向人工显示的问题 |
|---|---|
| `HARD_RISK` | 是否为重复订单、同一图片复用或其他硬风险；哪条证据可以证明通过或拒绝？ |
| `CROSS_ACCOUNT_ORDER_CONFLICT` | 不同账户出现同一订单号；哪一份申报拥有有效证据？ |
| `SAME_ACCOUNT_ACTIVE_ORDER_CONFLICT` | 同一账户存在活动中的相同订单号；是否为重复申报？ |
| 兼容旧 `held` | 根据AI理由显示原问题，并要求人工说明最终判断依据。 |

## 人工处理输入

人工选择“通过”或“拒绝”时必须填写：

1. **最终理由**：必填，去除首尾空格后至少5个字符。
2. **判断依据**：至少选择一项，包括订单号、金额、配送状态、平台、重复冲突、图片真实性或其他。
3. **拒绝类别**：拒绝时必填，沿用现有收据拒绝类别。
4. **人工修正字段**：需要通过但订单号或金额无效时必须补齐；可选修正店铺名称。

未满足上述条件时，前端按钮禁用，后端仍必须再次校验并拒绝请求。

## 状态与副作用

| 人工决定 | 状态变化 | 必须副作用 |
|---|---|---|
| 通过 | `on_hold → approved` | 重读当前状态；保存人工修正；执行订单号冲突保护；幂等发放积分；写审核日志；执行商品提取与推荐评价；发送现有通过通知 |
| 拒绝 | `on_hold → rejected` | 重读当前状态；保存拒绝类别与理由；写审核日志；发送现有拒绝通知 |

人工处理成功后，必须写入原AI日志的 `humanOverride`、`humanComment`、审核者和时间。由于学习队列只查询当前 `on_hold` 且未人工处理的记录，该订单会立即从暂挂列表和学习待审列表消失。任何副作用失败时不得提前把AI日志标记为已处理。

## 学习案例

只在上述学习队列记录被人工成功处理后写入 `ai_receipt_learning_examples`。案例必须使用 `errorType = manual_resolution_<reasonCode>`，并在 `learningNote` 中记录来源规则版本、AI问题点、人工判断依据与适用条件。

正式审核提示词只读取 `manual_resolution_%` 案例。历史普通AI纠错、自动通过、自动拒绝和非Pass 2日志即使存在，也不得作为此学习流程的输入。

管理员完成人工决定和必填理由即视为对该案例的人工确认。案例可停用并保留审计记录；不得删除原始审核日志，也不得让模型自行修改正式规则代码。

## 安全门禁

1. 所有接口仅管理员可用。
2. 处理前必须同时重读AI日志和收据状态。
3. 同一日志只能成功处理一次；重复请求返回已处理状态，不得重复发分或通知。
4. 通过操作不得绕过订单号冲突保护。
5. 学习样本保存失败必须记录错误并返回明确警告，已经完成的业务状态不得被伪装为未完成。
6. 全部时间以服务端时间记录，页面仅负责本地化显示。
