# TikTok竞品日报逐文件上传历史设计

## 问题结论

当前正式批次表已经保存`importedById/importedByName`，待确认草稿也保存`createdById/createdByName`，同步日志保存`actorId/actorName`。但是页面“同日导入批次”只查询当前选择日期；页面底部“日报历史与追溯”查询的是员工日报，不是文件上传。因此跨日期无法查看“谁上传了哪一份文件”。同日正式批次显示0，只能说明该日期没有成功正式批次，不能说明没有人选择过文件、保存过草稿或遇到解析失败。

现有上传流程还在识别失败前没有持久化记录；同一天不同用户上传相同文件时，会在正式批次重复检查处直接返回，第二位上传人不会进入草稿或同步日志。这与“每个人上传都会有记录”的要求不一致。

## 目标行为

系统新增独立的`upload event`台账。每次已认证且具备当天导入权限的用户调用文件上传接口时，先建立事件；之后根据结果更新为草稿已保存、草稿已恢复、正式提交、重复文件、用户放弃、识别拒绝或保存失败。正式批次仍按日期和文件SHA-256唯一，上传事件则按尝试独立保留，因此多人上传同一文件不会重复生成业务数据，但每位上传人的动作都可追溯。

| 字段 | 含义 |
|---|---|
| `attemptKey` | 每次服务端上传尝试的随机唯一键；旧数据回填使用`draft:<id>`、`snapshot:<id>`或`sync:<id>` |
| `reportDate`、`market` | 目标日报日期和市场 |
| `fileName`、`mimeType`、`fileSize`、`fileSha256` | 原文件元数据；无法安全取得的值保持空，不推测 |
| `actorId`、`actorName`、`actorEmail` | 实际上传登录账号 |
| `status` | `processing`、`draft_saved`、`draft_recovered`、`committed`、`duplicate`、`discarded`、`rejected`或`failed` |
| `draftId`、`snapshotId` | 对应草稿和正式批次；不存在时保持空 |
| `recognizedRows`、`excludedRows`、`shopCount`、`productCount` | 识别结果；解析前失败时保持空并显示“未保存”，绝不把未知当0 |
| `errorCode`、`errorMessage` | 结构化失败分类与脱敏后的安全说明；不记录文件内容、签名URL、凭据、SQL或内部堆栈 |
| `createdAt`、`completedAt` | 上传尝试与结果时间 |

## 写入顺序

上传接口在完成认证与当天早班/管理员权限校验后先写`processing`事件。扩展名、Base64、20MB、工作簿解析、可识别店铺等任何校验失败，都将事件更新为`rejected`后再返回用户错误。正式批次重复时更新为`duplicate`并关联已有`snapshotId`，不会再次保存文件或生成日报。草稿保存成功后关联`draftId`；提交、放弃或失败时由对应接口更新该草稿关联的事件。

初始事件写入失败时，不允许继续解析或生成正式批次，因为“业务数据存在但审计缺失”不符合要求。文件通过客户端格式/大小前置校验后直接交给服务器权威解析，避免浏览器本地解析失败而完全没有历史。业务事务已成功后，若事件状态更新暂时失败，不向用户误报业务失败；后续基于草稿、快照和同步日志的幂等对账会恢复真实状态。正式批次与日报的现有事务、HMAC/SHA校验、同日追加和不覆盖行为保持不变。

## 查询与页面

新增受保护的跨日期上传历史接口，管理员可查看全部上传人；普通已认证用户只查看本人。接口支持开始日期、结束日期、上传人、文件名、状态和最多200条。页面新增“文件上传记录”区，与“日报历史与追溯”分开，显示日期、上传人、文件、上传时间、结果、识别行、店铺/商品数、正式批次号和失败原因。

当天批次卡继续显示正式成功批次和上传人，用于对比；新历史区负责回答“谁上传过、何时上传、结果是什么”。空状态必须分别说明“没有上传记录”或“只有旧日报、没有可证明的文件上传人”，不能把未知显示为0次上传。

## 旧记录恢复边界

系统可以基于现有证据幂等回填：正式快照恢复为`committed`，草稿恢复为其当前状态，同步日志恢复为重复、失败或中断事件。上传人仅使用原表已有的`importedByName`、`createdByName`或`actorName`。如果旧行没有姓名、文件名、哈希或文件大小，页面显示“旧记录未保存”，绝不根据日报负责人、排班人员或店铺内容猜测上传人。

同一旧业务动作可能同时存在快照、草稿和同步日志。回填以各原始记录的确定性`attemptKey`保留来源，并明确标记为“旧证据恢复”；系统不会武断地把不同来源合并为一次，也不会把日报负责人当成上传人。不删除旧表、不修改历史日报、不生成根据信息不足的业务数据。

## 安全与兼容

所有接口继续使用Railway MySQL，绝不连接旧TiDB。未登录请求在数据库或存储操作前拒绝。普通员工不能查看其他人的上传历史，也不能提交或放弃他人的草稿。CSV、XLSX、XLS格式、同日多文件独立批次、服务器重解析、SHA-256、草稿恢复和事务回滚全部保持兼容。

本次修复不上传用户文件到生产，不创建测试批次、日报、店铺或商品。生产验收仅检查资源标记、健康和未登录权限；已认证历史数据由真实用户页面自行显示。
