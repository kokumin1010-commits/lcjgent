# 店铺协作日报输入与历史管理改进记录

## 概要

2026年9月18日，根据 `/master/store-management` 的实际使用反馈，修复“明日重点”输入时出现 `|||medium` 等内容、中文输入法组合文字被打断的问题，并补充协作日报的历史编辑、软删除和编辑人展示能力。实现继续遵守每店每日一份协作主日报、乐观锁、不可变版本和字段级审计的既有设计。

## 根本原因

“明日重点”和“需要公司／老板支持”使用竖线分隔的结构化文本。旧实现每次键盘输入都会立即把文本解析为对象，再将对象重新序列化回受控文本框。用户只输入一个字母或中文输入法尚未完成组合时，系统已经补入空负责人、空日期和默认优先级，因此 `d` 会被重写为 `d|||medium`，同时打断输入法的组合状态和光标位置。

历史列表虽然可以通过日期切换到旧协作日报，但没有明确的编辑入口，也没有删除接口。版本列表逐条保存操作者，但历史卡片只显示最后一次编辑人，不能直接看到所有参与编辑的人员。

## 实现内容

前端长文本字段增加独立原始草稿，并通过组合输入开始／结束事件保护中文输入法。输入期间显示用户原文，不再用结构化对象反向覆盖文本框；共享解析与格式化规则也不再为仅填写标题的事项强制显示 `|||medium`。完整格式仍支持 `事项|负责人|YYYY-MM-DD|优先级`，保存时继续由服务端严格校验。

协作日报历史卡片增加明确的“编辑”和“删除”操作。编辑会载入对应日期和当前版本，后续保存仍新增不可变版本，不覆盖版本表。删除经过浏览器二次确认，并由服务端在事务内执行软删除：记录删除时间、操作者和原因，版本号递增，追加 `deleted` 版本快照和生命周期审计，同时取消由该日报产生但尚未完成的 Todo；已完成 Todo 保留完成状态。

主日报读取、月度历史、经营总览、日报合规和连续缺报统计统一排除软删除记录。若同一日期后来重新填写，系统复用原主记录、清除删除标记并继续递增版本号，避免唯一键冲突，也保留删除前后的完整版本链。

历史卡片按日报汇总所有版本操作者并显示“编辑人”，选中日报后的“版本与字段留痕”区进一步显示每位编辑人的次数和逐版本时间。权限保持不变：只有店铺负责人或超级管理员可以保存、编辑和删除；普通已登录人员仍为只读。

## 数据库变更

`store_daily_master_reports` 新增 `deletedAt`、`deletedById`、`deletedByName` 和 `deleteReason`，并增加 `(storeId, deletedAt, reportDate)` 索引。升级键提升为 `store-business-command-center-v2`；缺失字段和索引通过 MySQL 命名锁下的幂等升级补齐，升级前执行加密备份，并校验店铺、上传、旧日报、协作日报、Todo、广告和达人相关记录数在结构升级前后保持一致。
